# Objects, Individually
Each object folder is self-contained: `model.blend` opens in Blender 4.0 or newer (timeline: closed at frame 1, inspection pose at frame 60, closed again at frame 120), and `model.urdf` loads on its own using only the local `assets/*.glb` meshes. Coordinates are metres, Z up, front toward negative Y. Masses and inertias are approximations.

These are original concept models in common product typologies, not replicas of any manufacturer's product.

## Layout

```
<category>/
  README.md                 overview with renders
  <id>-<slug>/
    model.blend
    model.urdf
    assets/*.glb            one mesh per link
    semantics.json          semantic annotation of each link (see below)
    README.md               joints and interaction frames
    NOTICE.md
    renders/rest.webp       closed
    renders/open.webp       moving parts open
```

`collection.json` lists every object with its id, category, size, joints, interaction frames and variant links. Each category names the `group` it belongs to: Furniture, Kitchen & Appliances, Tools & Workshop or Material & Logistics.

## Semantic annotations

Each object's `semantics.json` gives every link its [semantic_digital_twin](https://github.com/cram2/cognitive_robot_abstract_machine/tree/main/semantic_digital_twin) annotation, so the objects can be queried without parsing them:

- `object` gives the id, type, category and group, so the full chain is group → category → object.
- `annotations` lists the root link first (e.g. `Dishwasher`, `Cabinet`, or `NaturalLanguageWithTypeDescription` with its type for objects without their own class), then its moving parts (`Door`, `Drawer`, or `NaturalLanguageDescription` for knobs, levers and wheels) and the grip frames (`Handle`).
- `attached_to` is the link it hangs from in `model.urdf`.
- `part_of` is the whole it belongs to: a door's cabinet, a handle's door. It is `null` when no annotation has room for it, such as a knob.
- `annotation_classes` maps each annotation to its Python class.

The files are generated by `scripts/annotate_semantics.py --write-semantics` (needs `semantic_digital_twin`), and the tests fail when one no longer matches its model.

### Keeping in step with cram2

`semantic_concepts.json` names the class (concept) each object type should get and whether [cram2](https://github.com/cram2/cognitive_robot_abstract_machine) provides it: `available`, `missing`, or `unusable` (the class exists but cannot be attached to a body). An object whose concept is not `available` is annotated with the fallback class, and its `semantics.json` records the concept it waits for (`concept`, `concept_status`).

`scripts/sync_semantics.py` compares the registry with a cram2 checkout and prepares one small pull request per difference, never opening any itself:

```sh
python3 scripts/sync_semantics.py status  --cram <cram2 checkout>
python3 scripts/sync_semantics.py prepare --cram <cram2 checkout>   # writes semantic-sync/NN-<repo>-<change>/
```

| Change | Pull request to | What it does |
| --- | --- | --- |
| `add-class` | cram2 | adds a missing class from its `proposal`, with a test |
| `add-bases` | cram2 | gives an existing class the bases it needs to annotate a body |
| `adopt` | private_meshes | switches the objects to a class cram2 now provides |
| `withdraw` | private_meshes | falls back from a class cram2 no longer provides |
| `map-type` | private_meshes | assigns an existing cram2 class to an object type without a concept |

Each folder holds a `description.md` (the pull request's description, to paste on GitHub as it is), a `steps.md` (its title, branch and the commands to apply, test, commit and open it) and a `change.patch`. Every pull request touches only its own concept, so they can be reviewed and merged in any order. `prepare` recomputes everything on each run and replaces the folders of its previous run, so a merged change disappears on its own.

The loop for a new concept:

1. Add the object type to `object_types` and the concept with `"cram": "missing"` and a `proposal`. `status` lists every object type the registry does not mention yet, with similar existing concepts as a hint; map a type to `null` to keep it on the fallback on purpose.
2. Run `prepare` and open the cram2 pull request it describes, from the branch it names (`semantics/<change>`).
3. Later runs ask GitHub about that branch: while the pull request is open it is listed as waiting, once merged `prepare` offers the `adopt` pull request for this repository, and if it was closed without merging the concept counts as declined and is not proposed again. `--offline` skips the lookup; `GITHUB_TOKEN` raises GitHub's limit of 60 lookups an hour. To decline a concept without a pull request, set `"cram": "declined"` by hand; it is adopted anyway should cram2 gain the class later. The same script loads an annotated `World` (`load_annotated_world`) and draws an interactive graph of the whole collection (`--html`).
